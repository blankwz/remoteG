## 0. 结论（三选一：②部分通）

**结论 ②：部分通——装驱动需一次管理员授权（形态成立），但 v0.3.1 下「rd-agent 非管理员直控管道」不成立；换档不需要管理员。**

| 假设 | 实测结果 |
| :--- | :--- |
| 驱动安装需一次管理员授权（报告 §1.3 路线 B） | ✅ 成立。UAC 仅 1 次，全程 5.4s，无额外提示，无需 testsigning/bcdedit |
| 非管理员可直控管道建屏/撤屏（报告 §1.5 论断） | ❌ **v0.3.1 不成立**：`GENERIC_WRITE` 打开驱动命名管道即 `0x80070005`（管道默认 DACL 拒普通用户）；管理员同探针 3 轮全绿 |
| 换档需要 CCD/管理员（报告 §3 风险 3 疑问） | ✅ 半澄清：CCD（ChangeDisplaySettingsEx）换档**非管理员可调**，DISP_CHANGE=0，163~182ms——权限模型干净，换档与管道控制是两个独立权限面 |
| 建屏/撤屏稳定可重复 | ✅ 管理员上下文 3 轮全绿、无残留（非管理员被 DACL 挡在第一步） |

**一期启动建议**：按报告推进一期，`rd-vdisplay` 的管道客户端**按 master 版协议实现**（Notify 语义/多档/enabled/persist，与 snug 三层架构对齐），驱动分发二选一（见 §5 路线 A/B）；CCD 换档在 rd-agent 进程内直接做（已实证非管理员可用），与流管线重建解耦。

## 1. 环境与方法

- Windows 10 Pro 10.0.19045 x64，GTX 1060 6GB；用户 shell 非管理员（`net session` 失败 + 探针 `TokenElevation` 自检 `elevated=false` 双重实证）
- 本机已有两块第三方 IddCx 虚拟屏（OrayIddDriver / GameViewer）——与 virtual-display-rs 驱动**共存无冲突**（设备类同为 Display，设备名/硬件 ID 各异），间接证明本机 IddCx UMDF 管道健康
- 方法：独立 Rust 探针（v0.3.1 单向管道协议，`GENERIC_WRITE` 打开 + 消息模式写 JSON + FlushFileBuffers），系统侧验证用 `EnumDisplayDevices/EnumDisplaySettingsEx`（ACTIVE 适配器 diff 判定新屏），CCD 用 `ChangeDisplaySettingsExW`；管理员对照实验经 UAC 提权跑同一探针

## 2. 驱动安装实测（便携 zip 路线）

**流程**（v0.3.1 portable zip 内置七件：cer/bat/reg/uninstall.reg/cat/dll/inf）：

1. `certutil -addstore -f root DriverCertificate.cer` + `certutil -addstore -f TrustedPublisher ...`（证书双 store）
2. `reg import install.reg`（HKLM\SOFTWARE\VirtualDisplayDriver 数据键 + 事件日志源）
3. `nefconw --create-device-node --class-name Display --class-guid 4D36E968-... --hardware-id Root\VirtualDisplayDriver` + `nefconw --install-driver --inf-path VirtualDisplayDriver.inf`

**授权形态实测**：UAC 弹窗仅 1 次（提权入口），certutil/reg/nefconw 在管理员上下文零额外弹窗；setupapi.dev.log 实证 DriverStore 导入按 Authenticode（受信任发行者）通过——**与官方 README 口径一致，无需 bcdedit testsigning**（报告 §1.3 留意项落定）。

**踩坑 2 个（复现 rd 一期打包脚本时直接规避）**：

1. 中文 UTF-8 编码的 .bat 在 cmd GBK 控制台**静默失败**（前两次提权白弹，脚本没跑成）——安装脚本必须 GBK 或纯英文（与 RUN_LOG 既有教训同源）；
2. `nefconw --create-device-node` 缺 `--class-name Display` 时报 `Device Class Name missing` 失败（README 原文有此参数，报告 §1.3 摘录时漏了）。

## 3. 权限边界实证（核心结论数据）

| 实验 | 身份 | 结果 |
| :--- | :--- | :--- |
| `GENERIC_WRITE` 打开 `\\.\pipe\virtualdisplaydriver` | 非管理员 | ❌ `0x80070005 拒绝访问`（三次独立复现） |
| 同上 | 管理员 | ✅ 0ms 打开，命令生效 |
| CCD `ChangeDisplaySettingsEx` 换虚拟屏档位 | 非管理员 | ✅ DISP_CHANGE=0，182ms（660×990）+163ms（720×1080） |
| 同上 | 管理员 | ✅ 174ms avg |

**根因（源码级）**：v0.3.1 驱动创建管道未传 SECURITY_ATTRIBUTES（默认 DACL，UMDF 宿主身份创建）→ 普通用户无写权限；官方 GUI（v0.3.1）manifest 即 `requireAdministrator`——**v0.3.1 的官方产品语义就是「控制须管理员」**。master 分支已修：管道改 NULL DACL，注释明言「local account does not need admin privileges to use it」，且协议升级为 Notify/State/Event 双向（含在线改档）、新增 enabled/persist（HKCU 普通用户可写）——**但 master 修复尚未发版（latest release 仍为 v0.3.1）**。

## 5. v0.3.1 关键行为与缺陷清单（rd-vdisplay 设计输入）

1. **monitor id 即 IddCx ConnectorIndex，有效范围 0~9**（README「up to 10」）。实测 id=90：IddCxMonitorCreate 失败 → `monitor_object=None` → v0.3.1 `remove`/`remove_all` 对 None object **提前 return 不删条目** → 同 id 后续 Add 永久 no-op（脏状态）。实测 id=7 全绿。**rd-vdisplay 必须从 0 起分配 id 且做「建屏失败即弃 id」防御，或固定用低位段。**
2. 管道**单向**（服务端 INBOUND，客户端只写），无状态查询/回复/事件；`max_instances(1)`——同时仅一个客户端，须处理 `ERROR_PIPE_BUSY`（WaitNamedPipe 重试）。
3. 客户端必须 `SetNamedPipeHandleState(PIPE_READMODE_MESSAGE)`——否则服务端（消息模式）读不到消息边界，命令静默不生效（探针实测踩坑：写「成功」但屏不出现）。
4. **无在线改档协议**：Add 幂等（同 id no-op）。v0.3.1 在线换档唯一路径 = CCD（非管理员可用，§3）。master 的 Notify 协议支持在线改 modes 列表（驱动 departure+arrival 重建，非黑屏，窗口身份保留——snug-win 实证体验）。
5. 无 enabled/disable/persist 命令；驱动重启从 HKLM（管理员区）读初始屏列表。master 版 persist 写 HKCU（普通用户可写，rd-agent 运行时自持）。

## 6. rd-agent 接入路线（一期分发决策输入）

| 路线 | 形态 | 权限形态 | 代价 | 判断 |
| :--- | :--- | :--- | :--- | :--- |
| A. master 版驱动随包分发 | 自编译 master 驱动（NULL DACL + Notify 协议）打进球包驱动目录 | rd-agent 普通用户进程直控管道，全功能非管理员 | 需自建 WDK 构建链（本机已有 WDK 10.0.19041 Include 目录，链路完整性未验）；自签驱动签名面同路线 B | **首选评估项**：协议正对 snug 语义（多档在线换档），权限模型最干净 |
| B. 钉 v0.3.1 + SYSTEM 帮手 | 官方预编译驱动 + `vdd-user-session-service` 式 SYSTEM 服务代连管道（ImpersonateLoggedOnUser 读用户配置） | 管道命令走 SYSTEM，rd-agent 本体保持非管理员；CCD 换档在本体进程直接做 | 多一个常驻服务组件 + 单向协议局限（无在线改档，换档全走 CCD） | 官方组件现成（仓库内置），无构建链负担；协议局限可接受（换档走 CCD 已实证可用） |
| C. snug-win 路线（agent 整体提权） | rd-agent requireAdministrator | 全程管理员 | 违背 rd-agent「HKCU Run 普通用户进程」设计；UIPI 借口不成立（remoteG 不跨权限控窗是设计选择） | 排除 |

**CCD 换档的独立性是本次实测最重要的架构红利**：无论 A/B，换档都在 rd-agent 自己进程里完成（不需要提权、不需要管道），权限模型上「建屏/撤屏」（需要管道权限）与「换档」（用户会话级）天然分层。

## 7. 对预研报告结论的修正

- §1.5 论断「管道控制本身不需要管理员」**仅对 master 版成立**；v0.3.1（可分发版本）不成立（§3 实证）。snug-win 的 requireAdministrator 现在有了第二重解释：它分发 v0.3.1 驱动（其 release 资产 `virtual-display-driver-0.3.1-x64.zip`），普通用户进程连不上管道，整体提权顺带解决了这个约束——报告原判断「不是为了管道控制」需修正为「至少部分是为了 v0.3.1 管道 DACL」。
- §1.3 路线 B 的 nefcon 命令摘录缺 `--class-name Display`（§2 踩坑 2），一期打包脚本按 README 原文/本实测脚本为准。
- §3 风险 3 的 CCD 疑问解除：CCD 换档非管理员可用，不构成权限阻塞。
