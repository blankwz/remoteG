## 0. 结论

1. **Q1 可行，且有完整先例**：推荐直接复用 [MolotovCherry/virtual-display-rs](https://github.com/MolotovCherry/virtual-display-rs)（Rust、MIT、IddCx UMDF）。它原生支持「每显示器多分辨率、每分辨率多刷新率」，即 snug 的多档同比例模式；官方 Windows 版 snug（[nicocart/snug-win](https://github.com/nicocart/snug-win)）已用它在 UU远程 场景跑通建屏、同比例换档铺满全流程。不选 IddSampleDriver 自改造，也不选 RustDeskIddDriver（C++、能力面窄）。
2. **签名与安装是便携 zip 分发的重大约束，但已被 snug-win 实证出最低摩擦路线**：虚拟显示器驱动无法零摩擦随 zip 分发；自签证书 + 管理员一次性装入信任库 + 一键装驱脚本是验证过的方案。微软签名路线需 Hardware Dev Center + EV 证书，当前阶段不可行。
3. **Q2 改造面约 10 项，无一项为「大」除手势翻译（可后置）**：remoteG 已有窗口级会话骨架（OpenWindow/WindowEvent/FitMode）与尺寸变化即重建编码器的管线，虚拟屏接入的主要工作在新 crate 封装驱动控制面与会话编排，协议侧只是追加字段。

## 1. Q1：Windows 被控端能否稳定创建「手机比例」虚拟显示器并登记多档同比例分辨率模式

### 1.1 三路线对比

| 路线 | 技术形态 | 多档模式 | Rust 集成 | 分发成熟度 | 判断 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| virtual-display-rs | IddCx UMDF 驱动 + 命名管道 `\\.\pipe\virtualdisplaydriver` 控制 | 原生支持：至多 10 显示器、每显示器多分辨率、每分辨率多刷新率（README 明示） | 驱动为独立进程，控制面是管道客户端，Rust 直接实现 | 提供 MSI 与便携安装脚本，snug-win 以其为核心分发 | **首选** |
| RustDeskIddDriver | 微软官方 IndirectDisplay sample 改造的 C++ 驱动，新增 3 个 IOCTL（plug-in / plug-out / update-monitor-mode） | 有换模式 IOCTL，但多档登记能力未见文档明示 | 需自写封装层 + 自建编译签名链 | rustdesk 生产在用，但面向其自身安装器 | 备选，仅在 virtual-display-rs 出现阻塞时启用 |
| IddSampleDriver 自改造 | 从官方 sample 自写 | 全部自己做 | 全部自己做 | 全部自己做 | 工作量最大，无必要 |

推荐依据：snug-win 是 zephyr4123/snug 的官方认可 fork（GitHub parent 关系，MIT），其 README 明言不自研驱动、直接经命名管道按 SnugWin 归属 ID 创建并只清理自身虚拟屏——「1:1 承接 macOS 原版产品体验」的产品选择用现成驱动实现，等于替本项目验证了这条路。

### 1.2 多档模式：IDD 能否枚举多 mode 且切换不黑屏

**能，且已实证。** 证据链：

1. virtual-display-rs README：「Multiple monitors (up to 10)」「Multiple resolutions per monitor」「Multiple refresh rates per resolution」——多分辨率档位是驱动能力面的一等公民，不是技巧。
2. snug-win README：「对限定最小宽度的应用……自动把虚拟屏切换到恰好容纳它的同比例档位再铺满」——同比例换档在 UU远程 实时推流下实际可用。
3. macOS 侧同机制实测：换档约 0.4 秒、屏幕不掉线、编号不变、UU远程 不重新推流、点击位置保持准确（`<snug>/docs/how-it-works.md:58-66`）。Windows 侧 snug-win 复刻了同一交互，说明该体验可跨平台成立。
4. snug 建屏时登记全部档位、`maxPixels` 框住所有比例、换比例在线完成不换屏身份（`<snug>/docs/how-it-works.md:26-34`）——virtual-display-rs 的管道协议同样支持在线改分辨率列表，屏不掉线。

**与 macOS 的关键差异（对 remoteG 是利好）**：snug 的「换比例后 UU远程 要重选一次屏幕」（`<snug>/docs/how-it-works.md:78`）源于 UU远程 只在选中屏幕时按当时尺寸开始推流。remoteG 是自研双端：被控端自己开捕获会话，换比例/换档后由 Agent 主动重建捕获与编码管线即可，不存在「等第三方远控软件跟随」的问题。

### 1.3 签名与安装：对便携 zip 分发的约束（如实陈述）

**约束本质**：虚拟显示器驱动是装入系统驱动 store 的组件，必然触碰代码签名。两条路线：

**路线 A：微软签名（不可行，当前阶段）**。微软官方口径：Windows 10 起内核模式驱动必须经 Hardware Dev Center 签名，流程要求 EV 证书（[driver-signing 文档](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/driver-signing)）。IDD 是 UMDF 用户态驱动，理论上可走 attestation 签名绕开 EV（该细节页两次抓取失败，见 §4 未决），但 Dev Center 账号与费用对个人项目即是不小门槛。

**路线 B：自签证书 + 信任库（可行，snug-win 实证）**。virtual-display-rs 官方安装流程：

1. 把项目自签证书装入 `root` 与 `TrustedPublisher` 两个 store：`certutil -addstore -f root "DriverCertificate.cer"`、`certutil -addstore -f TrustedPublisher "DriverCertificate.cer"`；
2. 装驱动节点：MSI，或便携方式——设备管理器「添加旧版硬件」，或 nefcon CLI：`--remove-device-node` / `--create-device-node --hardware-id Root\VirtualDisplayDriver --class-guid 4D36E968-E325-11CE-BFC1-08002BE10318` / `--install-driver --inf-path <inf>`；
3. 需管理员权限一次性完成。

**snug-win 的便携分发实证**（直接可抄的答案）：

- 安装器路线：setup.exe（Inno Setup）内置 SHA-256 校验 + 证书指纹校验（`5DFA7E68997ED52D4B10420407860D1C29B6F427`）+ 静默安装，并在 `%ProgramData%\SnugWin\driver-ownership.json` 写归属标记，防止卸载误删用户自装的驱动；
- 便携路线：zip 内置 `driver\` 目录，设置页一键装驱，或手动管理员运行 `install-driver.cmd`；另有独立驱动包 `virtual-display-driver-0.3.1-x64.zip`。

**结论**：便携 zip 做不到「解压即用」，能做到的最低摩擦是「首次使用时一次管理员授权装驱」。这必须写进立项决策：接受则走 snug-win 便携路线；不接受则虚拟屏方向降级或改推安装器分发。

**边缘风险**：[virtual-display-rs issue #465](https://github.com/MolotovCherry/virtual-display-rs/issues/465)（2026-01）报告 Win11 ARM 等部分系统拒绝非 WHQL 签名的显示驱动——拒绝的是签名类型而非证书。x64 主流场景不受影响，立项时如实标注。另有个别社区口径称需 `bcdedit testsigning`，与官方 README 只要求装证书矛盾，以官方口径为准、实机验证时留意。

### 1.4 snug macOS 四条实测缺陷在 Windows 上的适配

| macOS invariant（pattern 卡实测） | Windows 是否存在 | 判断 |
| :--- | :--- | :--- |
| CGVirtualDisplay 必须主线程建/释放，不留局部强引用（私有 API 特性） | 无对应 | 不适用 |
| 建好不到 2.5s 就释放会卡死 WindowServer（minimumLifetime） | 无证据 | 不适用；实测时留意即可 |
| 物理尺寸按像素上限/220ppi 折算，按真机密度算屏永不上线且身份被拉黑 | 无对应 | virtual-display-rs 直接声明分辨率，无上线判定陷阱 |
| 换档/设回其他屏模式必须经帮手进程（主进程亲自切模式致释放拖 40s+） | 无对应证据 | 驱动天然在独立 UMDF 进程，主程序只是管道客户端，隔离是免费的 |

「登记多档、等真下线、固定身份防重复建屏」三条流程性经验仍然适用：建屏/撤屏后轮询等显示器真实出现/消失再做善后（窗口归位、模式恢复），是跨平台通用的时序防御（`<snug>/docs/how-it-works.md:33`；pattern 卡 `virtual-display-management` steps）。

### 1.5 Rust 集成面：Agent 进程内 vs 独立服务

**推荐：控制面在 Agent 进程内，驱动装/卸走独立安装动作。** 理由：

1. virtual-display-rs 的控制面就是命名管道客户端（发 JSON 命令），无状态、可随时断连重连——放进 rd-agent 一个模块（如 `rd-vdisplay`）即可，不需要常驻服务；
2. macOS 帮手进程模式的动机（主进程切模式污染释放时序）在 Windows 不存在（§1.4）；
3. 驱动安装/卸载是一次性管理动作，归安装器或设置页「一键装驱」（抄 snug-win），不进 Agent 运行时；
4. snug-win 的 requireAdministrator 是为了跨 UIPI 操控高权窗口与 CCD 设置，不是管道控制的需要；rd-agent 若不想整体提权，管道控制本身不需要管理员。

### 1.6 可直接移植的档位数学（ScreenFit）

`<snug>/Sources/SnugCore/PhoneScreen/ScreenFit.swift`（纯值类型，与显示器无关，pattern 卡 adaptationNotes 明言可独立移植）：基准 540×800、上限 1080 宽、步进 10、比例范围 1~2、`maxPixels` 2160×4320、UU 工具栏余量上下各 91 点、`width(toFit:)` 先乘后除防溢出。macOS 的 2 倍高清门槛（逻辑宽 ≥540、高 ≥800，`<snug>/docs/how-it-works.md:29`）是 macOS 行为，Windows 侧无需照抄，按 UU 推流缩放质量自定 hiDPI 档策略即可。机型库 `Assets/phone-models.json` 单一数据源 + 测试逐条校验的做法照搬（`<snug>/docs/how-it-works.md:74`）。

## 3. 风险与未决

1. **驱动安装摩擦**（§1.3）：便携 zip 无法零摩擦，需立项时明确接受「一次管理员授权」或改安装器分发。
2. **Win11 ARM 非 WHQL 拒装**（issue #465）：边缘场景，x64 主流不受影响，实机验证清单加一条。
3. **rd-agent 权限现状未核实**：换档若需 CCD（ChangeDisplaySettingsEx）或跨 UIPI 操控窗口，可能要求管理员；管道控制本身不需要。立项第一步应实测 rd-agent 非管理员下能否完成全流程。
4. **attestation 签名细节未直读**：driver-signing-policy 页两次抓取失败，UMDF 是否完全免 Dev Center 仅凭自签信任库装驱，以 snug-win 大规模分发事实为准（其即走自签路线）。
5. **捕获管线对新屏的适配**：WGC/DDA 对虚拟显示器的捕获路径需实机验证（CI 已知 WGC 在无 GPU VM 上有「API 可用但永不产帧」问题，虚拟屏可能新增类似边界）。
