# 01 阶段模型与端口契约

- 状态：规范性（Normative）。MUST/MUST NOT/SHOULD 按 RFC 2119 语义使用。
- 版本：0.1

## 1. caps 系统

所有端口用**结构化能力描述**协商。caps 是可序列化 JSON/Rust 结构，字段一律「数值或区间」，不允许自由文本。

### 1.1 协商规则（谓词语义）

| 字段角色 | offering（提供方） | requirement（消费方） | 判定 |
|---|---|---|---|
| `Option<T>` 类（datagram/streams） | `None` = **不支持** | `None` = 不限制 | req 有值时 offering 必须有值且逐子字段 ≥ |
| 数值类（mtu） | 实测值 | `0` = 不限制 | `offering ≥ requirement` |
| 集合类（congestion） | 支持列表 | 空列表 = 不限制 | `requirement ⊆ offering` |
| bool 类（multipath） | 能力 | `false` = 不限制 | `offering ≥ requirement` |

1. 任一有值 requirement 不满足 → 协商失败。
2. 协商失败是**编辑期错误**（Studio 标红）与**运行期回退信号**（计划回退到下一条 path），不是 panic。
3. caps 结构带 `caps_version`（当前 1）；主版本不同的 offering/requirement 直接失败，不做兼容猜测。

### 1.2 公共 caps 字段（全部阶段可用）

```jsonc
{
  "mtu": 1200,                  // 本段路径最大传输单元（MUST，S4 输出必须如实上报）
  "loss_ratio": 0.02,           // 先验丢包率（S1/S2 提供，SHOULD）
  "rtt_ms": 80,                 // 先验 RTT
  "cost": 3,                    // 成本先验：0=loopback 1=LAN 2=WAN直连 3=中继 9=未知
}
```

## 2. 数据类型

```rust
/// S1 产出：候选端点
pub struct EndpointCandidate {
    pub addr: SocketAddr,          // IPv4/IPv6
    pub proto: Proto,              // Udp | Tcp | Both
    pub source: SourceKind,        // Lan | Rendezvous | Stun | Dns | UserManual
    pub cost: u8,                  // 0 loopback / 1 lan / 2 wan / 3 relay / 9 unknown
    pub ttl: Option<Duration>,     // 候选有效期（LAN 候选通常 30s）
}

/// S2/S3 产物：已验证的原始管道
pub struct PathHandle {
    pub socket: Arc<dyn PathSocket>,   // 已连通/已绑定的收发原语
    pub kind: PathKind,                // Direct | Relay
    pub via: &'static str,             // 模块 id
    pub measured: Measured,            // 握手期实测：rtt、mtu(带外探测)、loss
    pub addr: Option<SocketAddr>,      // 对端地址（真实传输建立用；Loopback 为 None）
}

/// S4 产物：统一传输面
pub struct Channel { /* 见 §6 */ }
```

**PathKind 枚举**（遥测 `path.kind` 与 manifest `requires.path` 共用，不得新增私有值）：
`Direct`（打洞产物）| `Relay`（中继产物）| `Loopback`（进程内参考实现，T0 剖面专用）。

**Measured 字段表**（握手期实测，供传输面做先验）：

| 字段 | 类型 | 语义 |
|---|---|---|
| `rtt_ms` | f32 | 打洞/中继握手期 EWMA RTT（α=1/8，03 篇口径） |
| `mtu` | u16 | 带外 PMTUD 探测结果（§4.1-6）；`0` = 未探测 |
| `loss_ratio` | f32 | 握手窗口丢包率 |

**PathSocket trait**（原始管道收发原语；真实打洞/中继模块注入 UDP/TCP socket，参考实现为内存管道）：
`send_to(data, peer)` / `recv_from(buf)`。v0.1 中 `PathHandle.socket` 允许 `None`（仅限 Loopback）；0.2 起 Direct/Relay MUST 携带。

## 3. S1 Discovery 端口

```rust
#[async_trait]
pub trait Discoverer: Send + Sync {
    fn caps(&self) -> &DiscoverCaps;            // { scope: Lan|Tailnet|Public, zero_conf: bool }
    /// 订阅候选流；模块 MUST 持续刷新并在候选失效时发出 Lost 事件
    async fn watch(&self) -> Result<BroadcastStream<EndpointEvent>>;
    async fn poll_once(&self) -> Result<Vec<EndpointCandidate>>;  // 一次性拉取（供 bench）
}
```

MUST：只应答不主动广播敏感信息（rd LAN 发现的安全基线：应答内容 = 连接握手本就公开的主机名/指纹短 hex/端口）；发现 ≠ 信任。

## 4. S2 Punch 端口

```rust
#[async_trait]
pub trait Puncher: Send + Sync {
    fn caps(&self) -> &PunchCaps;   // { proto, symmetric_attack: None|Birthday|PortPredict, needs_rendezvous: bool }
    /// 用候选地址打洞；允许并发多候选。必须在 budget 内返回确定结论。
    async fn punch(&self, ctx: PunchCtx, peers: Vec<EndpointCandidate>,
                   budget: Duration) -> PunchOutcome;
}
pub enum PunchOutcome { Connected(PathHandle), Failed(FailReason), BudgetExhausted }
```

### 4.1 打洞规范性 MUST（源于 RustDesk CGNAT PoC #16488 的教训）

实现 S2 的模块 MUST 满足——这是本规范**唯一的算法级强制**，因为它是已被真实失败验证的根因修正（RustDesk master v4 路径已据此修复，残留缺陷见 docs/cards/rustdesk-punch.md）：

1. **同 socket STUN**：用于打洞的 socket 必须自己执行 STUN 获取映射，MUST NOT 复用其他协议（如 TCP 会合连接）观察到的端点推断 UDP 映射；
2. **完整端点交换**：双方交换完整 `ip:port`（而非只换端口）；
3. **双向同时发送**：两侧在协商窗口内对发（至少 8 包、间隔 ≤100ms）；
4. **首包权威**：收到对方第一个有效包后，以该包的真实源地址为准更新对端地址，丢弃此前推断；
5. **绑定保活**：直连建立后周期发包维持映射；周期 = min(15s, NAT 超时 × 0.5)。NAT 超时测量程序：以 2s 间隔对测绘端点发包直至对端不再可达（连续 3 包无应答），取首次无应答前的时间；无测量条件时用默认 15s。
6. **MTU 联动**（评审新增）：直连建立后 MUST 立即做带外 MTU 探测（DF 位递增探测或 DPLPMTUD），结果写入 `PathHandle.measured.mtu`；S5 的「分片头 + payload + 28B IP/UDP 开销」MUST ≤ 该值——否则隧道/PPPoE 下静默丢包（rd QUIC MTU 10040 事故的教训）。

SHOULD：对称 NAT 支持生日攻击式多端口猜测（Tailscale 方案）；IPv6 与 IPv4 **并行发起**打洞（v6 命中作 tie-break 优先，而非串行偏好）；容忍 Windows 下 ICMP unreachable 噪声（首包即判失败）。

## 5. S3 Relay 端口

```rust
#[async_trait]
pub trait Relay: Send + Sync {
    fn caps(&self) -> &RelayCaps;   // { proto: Tcp|Quic|Turn|Custom, regions, auth }
    async fn alloc(&self, ctx: RelayCtx, peer: &PeerId) -> Result<PathHandle>;
    /// 中继质量先验（用于计划排序与码率上限预估）
    fn quality_hint(&self, region: &RegionId) -> QualityHint;
}
```

MUST：中继分配失败必须可探测（超时 ≤ budget）；`PathHandle.kind = Relay` MUST 如实标注——下游码控有权据此降码率（P4：中继是常态语义）。

## 6. S4 Transport 端口与 Channel 契约（规范核心）

```rust
#[async_trait]
pub trait Transport: Send + Sync {
    fn caps(&self) -> &TransportCaps;
    /// 消费 1..n 条 PathHandle（可多路径竞速），产出统一 Channel
    async fn establish(&self, ctx: TransportCtx, paths: Vec<PathHandle>) -> Result<Channel>;
}

#[derive(Clone, Serialize)]
pub struct ChannelCaps {
    pub datagram: Option<DatagramCaps>,   // 不可靠数据报
    pub streams: Option<StreamCaps>,      // 可靠有序流
    pub congestion: Vec<CongestionKind>,  // Cubic | Bbr | …
    pub mtu: u16,                         // 实测路径 MTU
    pub multipath: bool,
}
pub struct DatagramCaps { pub max_size: u16, pub lossy_ok: bool }   // lossy_ok=true 表示发送方可接受丢弃
pub struct StreamCaps { pub reliable_ordered: bool, pub bidi: bool, pub max_concurrent: u32 }

impl Channel {
    pub fn caps(&self) -> &ChannelCaps;
    pub async fn send_dgram(&self, b: Bytes) -> Result<()>;       // 需要 datagram caps
    pub async fn recv_dgram(&self) -> Result<Bytes>;
    pub async fn open_stream(&self, kind: StreamKind, o: StreamOpts) -> Result<Stream>;
    pub async fn accept_stream(&self) -> Result<(StreamKind, Stream)>;
    pub fn stats(&self) -> StageStats;                            // 03 篇契约，MUST
    pub fn on_stats(&self, h: impl FnMut(StageStats) + Send + 'static);
    pub fn close(&self, code: u32, reason: &str);
}
```

MUST：

1. Channel 建立后、放行业务数据前，必须完成指纹互认（§7）；
2. `send_dgram` 在队列超限时 MUST 丢新包并返回 `WouldBlock`（**不可阻塞等待**——这是与可靠流的本质区别，S5 的丢帧策略依赖它）；
3. `stats()` 必须反映真实路径（direct/relay 如实标注）；
4. 流（stream）与数据报（datagram）必须可共存于同一 Channel（控制面走流、媒体走数据报，是推荐组合）。

MUST NOT：Transport 不得在内部做媒体语义（分帧/FEC/码控）——那是 S5 的职责。**反例**：把 Moonlight 的 RTP 分片做进 transport 层，会使其无法搭配 QUIC 使用。

## 7. 安全基线（跨阶段）

- 身份：每端持有长期身份密钥；对端以**指纹钉扎**识别（TOFU + 配对码确认，或预共享指纹）。
- 配对码：6 位数字、短时效、单次（rd 已验证的家人友好模式，定为推荐档）。
- Channel 握手：`IdentityHello{fp, device_name, protocol_version}` → 双向校验 → 才允许 S5/S6 数据。指纹不符 MUST 立即 close（code=4xxx）。
- 中继保密：Relay MUST NOT 能解密业务流量（hbbr/DERP/TURN 均满足：密钥在端上协商）。

## 8. S5 MediaAdapt 端口

```rust
#[async_trait]
pub trait MediaAdapt: Send + Sync {
    fn caps(&self) -> &MediaCaps;
    // { fec: {scheme: None|Xor|ReedSolomon, max_overhead: f32},
    //   recovery: {on_frame_loss: IdRequest|Ltr|TileRefresh, idr_cost_estimate_ms},
    //   shard_size: u16, pacing: bool }
    fn tx_path(&self, ch: Arc<Channel>, cfg: MediaConfig) -> Box<dyn FrameSink>;    // Frame → 分片+FEC+发送
    fn rx_path(&self, ch: Arc<Channel>, cfg: MediaConfig) -> Box<dyn FrameSource>;  // 分片 → Frame | FrameLost
}

pub trait FrameSink: Send {
    /// 提交一帧；返回排队深度供码控消费。队列超限（WouldBlock）时本帧 MUST
    /// 被整体放弃（含已发分片的 loss 标记事件），MUST NOT 阻塞、MUST NOT
    /// 误报为 Closed——调用方据此跳过该帧继续下一帧。
    async fn submit(&mut self, frame: EncodedFrame) -> Result<QueueDepth>;
    fn set_target(&mut self, kbps: u32, fps: u32);          // 码控入口
    fn request_recovery(&mut self, kind: RecoveryKind);     // 接收侧驱动恢复
}
```

规范认可的三种已验证策略组合（登记为 profile，模块声明实现哪个）：

| profile | 传输面 | 丢包应对 | 恢复 | 出处 |
|---|---|---|---|---|
| `fec-shards` | datagram | FEC（Reed-Solomon 型，比例可协商 ≤200%；XOR 为最小参考实现） | LTR/参考帧失效，避免整帧 IDR | Moonlight |
| `reliable-idr` | stream | 无（可靠流重传） | 陈旧帧丢弃 → 下帧 IDR | rd 现状 |
| `hybrid` | datagram+stream | **NACK 选择重传 + FEC**：按 RTT/丢包动态切权重（WebRTC 同款），帧走 datagram | LTR 优先，IDR 兜底 | v0.2 目标 |

### 8.1 输入通道契约（评审新增）

高频输入（鼠标/触摸）MUST 优先走 **不可靠 datagram + 合并（coalesce）语义**：同一逻辑设备的连续事件允许覆盖（丢旧留新），接收端以最新事件为准；离散事件（按键/点击）走可靠流。理由：输入走可靠流会造成 HOL 阻塞（Moonlight 实证：批量触摸/鼠标走不可靠包，InputStream.c）。

### 8.2 接收缓冲（评审新增）

`FrameSource` 实现必须声明接收缓冲能力：乱序容忍窗（帧数，≥1）与缓冲深度（1-3 帧）。容忍窗内的迟到分片参与恢复；窗外才判帧丢失。缓冲深度进遥测 `extra.recv_buffer_depth`。

## 9. S6 Codec 端口（能力契约）

Codec 阶段 v0.1 只定**能力契约与参数档**，不定实现接口（各编码器差异大，强行统一会引入抽象税）：

```jsonc
{
  "codec": "h264", "profile": "high",
  "hw": "nvenc|qsv|amf|mf|none",
  "low_latency": ["no_b_frames", "cbr", "no_lookahead", "intra_refresh?"],
  "keyframe": "on_demand",           // 周期性 | 按需（MUST 默认按需）
  "ltr_frames": 3,                   // 0 = 不支持
  "decode_compat": "webcodecs:h264"  // 声明浏览器/客户端可解性
}
```

参数档（预设，源自 Sunshine/NVENC 低延迟实践，SHOULD）：`h264.ultralowlat`（P1-P3 档、CBR、0 B 帧、无 lookahead）、`h264.balanced`、`h264.lan444`（LAN 高带宽模式，4:4:4/高码率，Pyrowave 定位的低成本近似）。
