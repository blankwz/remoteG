# 00 总览与设计原则

- 状态：规范性（Normative）
- 版本：0.1（2026-10-24）

## 1. Switchboard 是什么

一套**面向交互式远控/低延迟流媒体**的模块化规范：定义 6 个流水线阶段的端口契约（接口 + 能力协商 + 统一遥测）、一门声明式连接计划语言、一套基准与评分标准。任何满足阶段契约的实现（无论来自 RustDesk、Moonlight、Tailscale 还是自研）都可以互相替换、组合与横向评测。

```
┌─────────────────────────── Switchboard 规范栈 ───────────────────────────┐
│  L3 编排   Connection Plan (TOML) + Studio 可视化 + 执行器              │
│  L2 契约   阶段端口 trait + caps 协商 + 遥测契约 (本规范核心)            │
│  L1 实现   native-rust / wasm(component) / process(外部栈) 三种绑定      │
│  L0 评测   SB-Bench 负载 + 指标 + 评分 → bench.json（可比性的唯一依据）  │
└──────────────────────────────────────────────────────────────────────┘
```

## 2. 非目标（防止规范膨胀）

- **不是线路协议**：不规定线上字节格式；各家线上格式留在各自模块内部。
- **不重写实现**：规范靠 adapter 适配既有代码（含 process 绑定整栈接入），不要求重构上游。
- **不约束应用层**：输入注入、剪贴板、终端语义在阶段 S6 之外（仅预留 Session 钩子）。
- **不做通用插件市场治理**：签名、分发、安全审计交给注册表运营方。

## 3. 六阶段模型

一次远控连接 = 以下阶段的**有向组合**（非全必需）：

| 阶段 | 名称 | 职责 | 输入 → 输出 | 参考实现（已在调研中确认） |
|---|---|---|---|---|
| S1 | Discovery 发现 | 产出对端候选地址 | — → `Vec<EndpointCandidate>` | LAN UDP 广播（rd）、mDNS、rendezvous（RustDesk hbbs）、MagicDNS |
| S2 | Punch 打洞 | 用候选地址打出直连 PathHandle | candidates → `PathHandle?` | RustDesk punch（修正版铁律）、ICE、Tailscale DISCO（process） |
| S3 | Relay 中继 | 打洞失败时分配中继 PathHandle | peer-id → `PathHandle` | DERP（Tailscale）、hbbr、TURN、SDR |
| S4 | Transport 传输 | 把 1..n 条 PathHandle 变成多路复用、拥塞受控、有统一统计的 `Channel` | `Vec<PathHandle>` → `Channel` | quinn QUIC（rd）、KCP（RustDesk）、ENet/RTP（Moonlight）、SRT、TCP+TLS |
| S5 | MediaAdapt 媒体适配 | 帧 ↔ 分片打包、FEC、丢帧与恢复策略、码控 | `Frame ↔ Shard` + 遥测 → 策略 | Moonlight FEC 分片+RFI、rd 可靠流+IDR、H.264 码控 |
| S6 | Codec 编解码 | 像素 ↔ 码流（能力契约 + 低延迟参数档） | `Frame ↔ AU` | NVENC/QSV/AMF（Sunshine 参数档）、OpenH264、WebCodecs 对齐命名 |

安全基线（跨阶段 MUST）：任何 `Channel` 上承载业务数据前，必须完成**指纹钉扎互认**（TOFU + 6 位码配对或预共享指纹），见 01 §7。

## 4. 设计原则（规范论证）

| # | 原则 | 论证（来源） |
|---|---|---|
| P1 | **caps 协商而非统一 API** | Moonlight 必须 datagram+FEC、rd 现状是可靠流——统一 API 会抹平本质差异；GStreamer caps 模型证明"能力交集"可组合异质元件 |
| P2 | **计划可移植** | "先中继后升级直连"（Tailscale、Steam SDR 同构）本质是计划语义而非实现细节；写成声明可跨实现复用 |
| P3 | **遥测是一等公民** | 无法统一测量的模块无法评测与 A/B（SB-Bench 的前提）；AIMD/QoS 控制环也消费同一遥测 |
| P4 | **失败是常态语义** | 打洞失败→中继、中继劣化→码率上限、丢帧→恢复策略：一切降级都是契约的一部分，不是异常 |
| P5 | **适配三种绑定** | 巨型栈（Tailscale/SDR/libwebrtc）不可能重写进 SDK；process 绑定让"整栈即模块" |
| P6 | **最小强制** | 合规分级（06 篇）：只吐 caps+遥测即可入册（L-A），避免"规范大到没人实现" |

## 5. 关键抽象一览

- [`EndpointCandidate`](01-阶段模型与端口契约.md)：候选端点（addr + 来源 + 成本先验 + TTL）
- [`PathHandle`](01-阶段模型与端口契约.md)：已验证的原始管道（打洞/中继产物，供 Transport 消费）
- [`Channel`](01-阶段模型与端口契约.md)：统一传输面——datagram（可选）+ 流（可选）+ 指纹互认 + 统一遥测
- [`StageStats`](03-遥测与统计契约.md)：统一遥测帧（JSON schema v1）
- [`ConnectionPlan`](02-连接计划-Plan-DSL.md)：声明式多路径计划（TOML），Studio 的编辑对象
- [`bench.json`](04-基准与评分标准.md)：SB-Bench 产出，模块注册表的评分依据

## 6. 术语

- **caps**：结构化能力描述（可 offering 可 requirement），协商 = 交集非空。
- **direct / relay / loopback**：路径三种来源；遥测中必须标注。
- **绑定（binding）**：模块的落地形态——`native-rust`（进程内 crate）、`wasm`（组件模型）、`process`（外部进程/服务）。
- **合规等级**：L-A（登记）/ L-B（单阶段可用）/ L-C（全计划 + 基准认证）。
